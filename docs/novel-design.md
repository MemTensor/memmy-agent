# 小说写作系统设计文档（Novel System Design）

> 基于 memmy-agent 源码实测调研（2026-08-13）· 二次开发施工图
> 仓库策略：Fork 官方 MemTensor/memmy-agent → `develop` 分支承载全部开发

---

## 0. 项目定位

在 memmy-agent（本地优先的 Agent 记忆 + 运行时）之上，二次开发一套**编委会制小说写作系统**：

- **主编中枢**负责任务下发、进度监控、中间结果审阅、采纳/驳回决策、工作流编排
- **创作八将**沿 Pipeline 顺序协作（灵思→构世→塑像→谋篇→埋线→执笔→淬文→审校）
- **支撑四翼**横向服务（布景/监工/装帧/试读）
- 运行模式：**半自动**——方向类决策由用户确认，执行类工作自动运行

### 0.1 要解决的六大结构性痛点（专业作者视角）

| # | 痛点 | 现象 | 系统对应解法 |
|---|---|---|---|
| 1 | 长篇连贯性崩坏 | 超 10 万字后遗忘前文设定、世界观自相矛盾、配角"死而复生" | 事中一致性引擎（§6）+ 每书记忆隔离（§4）+ 双基准查重 |
| 2 | 角色崩坏/人设漂移 | 标签式人设（高冷/腹黑），行为无心理逻辑，20 章后判若两人 | 塑像人物中心（人物卡+成长弧）+ 路由 C 人设纠偏（§6） |
| 3 | 伏笔丢失/逻辑断层 | 第 3 章埋的槐树根，第 12 章在沙漠挖出（地理崩坏） | 19 线叙事矩阵 + 伏笔状态机（§2.6）+ 埋线/审校共同维护 |
| 4 | AI 味重 | 满屏"不禁/仿佛/那一刻"；逻辑过载、经验真空、缺具身化细节 | 去 AI 味引擎三道防护（§7）+ 具身细节库（§3.2） |
| 5 | 工作流碎片化 | 大纲/起草/编辑/导出多个工具切换，交接丢上下文 | 单一创作工作台：立项→蓝图→细纲→写作→交付全流程内聚 |
| 6 | 设定无版本/无基线 | 改设定引发全线返工，或随意乱改破坏已写内容 | Plot Git 基线锁定（§5）：前置锁定，修改走新版本线 |

### 1.4 融合决策记录（相对初版 11 位专家）

- 谋篇 = 剧情架构（PA）+ 大纲规划（OP）合并——一体两面
- 淬文 = 文笔润色（PP）+ 对话编剧（DW）合并——同属语言加工层
- 开篇拆两半：**写**归执笔、**验**归试读——创作者不自己审自己
- 爽点拆两半：**设计**归灵思、**度量**归监工——设计靠感觉、度量靠数据
- 爆款拆解拆两半：数据复盘归监工、对标素材沉淀进素材库
- 新增埋线（伏笔是网文命脉，独立成专家）；新增布景（场景是 AI 写作弱项，值得专项）

## 2. 工作流引擎与主编控制台
### 2.0 三环架构总览（立项环 / 创作环 / 交付环）

```
┌─ 立项环（一次性 · 产出即锁定）─────────────────────────┐
│ 入口触发 → 灵思产出 3 个方案卡片 → 用户选择/混选 →      │
│ 生成【基线快照】→ 前置设定全部锁定（不可变基线）          │
└──────────────────────────────────────────────────────┘
┌─ 创作环（长期 · 事中纠偏为主）─────────────────────────┐
│ 蓝图：19 维线索矩阵 + 分卷大纲（卷级锁定）              │
│   → 细纲：章节任务单（3-4 场景 + 控字预算 + 伏笔插针）  │
│   → 写作：控字正文 + 去 AI 味实时洗稿 + 划词重写/人机接管│
│   → 拦截：一致性引擎事中路由 → 知识中心修正 → 重流      │
└──────────────────────────────────────────────────────┘
┌─ 交付环（每章/每卷/完本）─────────────────────────────┐
│ 审校终验（双基准全量查重）→ 试读 → 装帧交付 → 监工复盘  │
│ → 复盘数据反哺节奏矩阵与灵感库                          │
└──────────────────────────────────────────────────────┘
```

- **入口触发**（立项环起点）：①一句话直接立项；②灵感库推荐卡片**套用**；③多张灵感卡片**对撞**（创意杂交）
- **方案卡片**：灵思基于入口产出 **3 个创作方案卡片**供用户选择/混选，每卡含：作品基础信息（作品名/频道/核心题材/目标篇幅/商业卖点）、故事梗概与核心动力（Logline/300 字梗概/核心驱动力）、金手指与规则机制（能力/底层逻辑/代价与上限）、核心角色卡片（主角/反派/女主或搭档/NPC 群像）、世界观基石（力量境界/社会矛盾/地理舞台）、连载节奏（节奏模板+参数）
- 选定后生成**基线快照**，前置设定全部锁定（改设定 = 新建版本线，见 §5）

### 2.1 AG-UI 人类决策层（交互底座）

> 半自动模式的"关键节点人工确认"通过 AG-UI（Agent-User Interface Protocol）标准化实现：
> Agent 在决策点发出结构化交互请求 → 前端渲染成决策卡片 → 用户操作 → 结构化响应回传 → Agent 恢复执行。

**SDK 三层分工与本系统取舍**：

| 层 | 作用 | 本系统策略 |
|---|---|---|
| ag-ui/core | 协议核心：消息类型/schema/校验/状态机 | ✅ 采用官方协议定义（避免自造轮子后与标准脱节） |
| ag-ui/client | 前端渲染：决策卡片组件 | ⏳ 起步自绘 React 卡片，后期可平滑换官方组件 |
| ag-ui/agent | Agent 端发消息/暂停/恢复 | 🔧 自建 `agui-bridge.ts` 对接 memmy 运行时（官方 agent 库难嵌入自定义运行时） |

**决策点映射**（人类决策全部走 AG-UI 卡片）：

| 系统场景 | AG-UI 交互 | 用户操作 |
|---|---|---|
| 立项入口（一句话/灵感卡套用/对撞） | `form` | 输入创意或选择灵感卡片 |
| 方案卡片选择（灵思产出 3 个） | `multi-select` | 选方案 / 要求改 |
| 5 个半自动确认节点（立项/设定/大纲/开篇/卷末） | `confirm` + 详情卡 | 采纳 / 驳回（附原因） |
| 主编驳回路径 | `question` | 打回上一节点 or 打回灵思 |
| 基线锁定确认（选方案后） | `confirm`（不可逆提示） | 确认锁定 |
| 章节审校结果 | 批注列表 + `confirm` | 逐条采纳 / 驳回 / 一键修改 |
| 试读 / 装帧交付 | `confirm` + 预览 | 放行 / 打回 |
| Plot Git 分支试错 | `confirm` | 合并 / 丢弃分支 |

**与 memmy 运行时对接**：

- Agent 端：`src/novel/agui-bridge.ts` —— 决策点发出 AG-UI 消息 → 挂载于现有 Inbound/OutboundMessage（扩展 `agui` 消息类型）→ 经现有 SSE 事件流送达前端
- 中断/恢复：AG-UI interrupt 与 session-dag 节点状态打通（等待决策 = 节点 blocked，收到响应 = 恢复 active）
- 前端：`components/agui/` 决策卡片组件，挂载进主编控制台与写作工作台

### 2.2 Pipeline 编排（核心机制）

```
灵思 → 构世 → 塑像 → 谋篇 → 埋线 → 执笔 → 淬文 → 审校
 │       │      │      │      │      │      │      │
 └─ 主编在每个节点后：审阅中间结果 → 采纳（放行）/ 驳回（打回）
```

- 顺序协作默认严格串行（下游依赖上游产出），支撑四翼随时可并行介入
- **锁定**：节点被锁定（frozen）时即使上游变更也不重跑，防止"改了设定引发全线返工"
- **中断/恢复**：任何节点可中断，状态持久化（快照），恢复后从断点继续
- **驳回路径**（待定，默认打回上一节点）：默认打回上一节点修订；用户可选打回灵思整体重想

### 2.3 主编控制台功能清单

| 功能 | 说明 |
|---|---|
| 任务下发 | 带《创作指令单》（目标/约束/参考素材/验收标准）派单 |
| 进度监控 | 各节点状态、各专家调用记录、token 消耗 |
| 中间结果审阅 | 每节点产出先呈主编（人工）过目，再决定采纳/驳回 |
| 采纳/驳回决策 | 采纳→放行下一节点；驳回→打回指定节点，记录驳回原因 |
| 中断/恢复/锁定 | 任意节点三操作 |
| 多书切换 | 命名空间隔离，控制台一键切换项目 |

### 2.4 章节状态机（与伏笔状态机并列）

```
规划中 → 写作中 → 待审 → 已采纳 / 已驳回 → 已发布
              ↑__________ 打回修订 __________↓
```

### 2.5 伏笔状态机（埋线 + 审校共同维护 · 线索矩阵的原子单元）

```
埋下 → 待回收 → 已回收
 │        │
 │        └─ 回收逾期预警（监工定期扫描，提示主编）
 └─ 追踪字段：伏笔内容 / 埋设章节 / 计划回收章节 / 实际回收章节 / 责任人
```

| 关系羁绊 | family | 家庭线 | 家人状态 / 家族事务 |
| 关系羁绊 | romance | 爱情线 | 感情进展 / 误会与和解 |
| 关系羁绊 | friendship | 友情线 | 伙伴关系变化 |
| 关系羁绊 | colleague | 同事线 | 同门 / 同僚 / 团队协作 |
| 关系羁绊 | enemy | 敌人线 | 敌人动向 / 仇恨升级 |
| 策略局势 | game | 博弈线 | 多方博弈 / 棋局推进 |
| 策略局势 | system | 体制线 | 门派 / 王朝 / 组织规则与斗争 |
| 策略局势 | ability | 能力线 | 能力成长 / 新能力觉醒 |
| 策略局势 | cost | 代价线 | 金手指代价 / 牺牲与代价积累 |

| 剧情推动 | break | 破局线 | 破局 / 反转 / 高潮爆发 |
| 叙事内核 | motif | 核心意象线 | 反复出现的意象 / 主题（剑、雪、槐树…） |
| 叙事内核 | timeline | 农历/时间线 | 时间流逝 / 节气 / 时限压力 |

```json
{
  "line_type": "romance",
  "name": "爱情线",
  "category": "关系羁绊",
  "status": "活跃",            // 活跃 / 蛰伏 / 回收 / 完结
```

## 3. 三大数据库（参考资料层 · 后台维护 · 静态参考）

> 三大库是后台人工收集整理的**参考资料**，为专家提供创作知识参考；它们是**输入侧知识库**，
> 永不接收创作产物 —— 创作产物（作品设定/人物/伏笔/正文）全部进作品数据层（见 §3.3 / §4）。

### 3.1 世界库（分两大类：现实世界 / 虚拟世界）

| 大类 | 内容 |
|---|---|
| 现实世界 | 历史、地理、职业、法律、时代背景、真实事件等现实知识 |
| 虚拟世界 | 规则、地点、势力、历法、能力体系、种族、科技树等架空设定知识 |

- 世界库规则 = **预设硬约束**（如"该世界无魔法"，正文就不许出现魔法）
- 数据来源：后台人工收集整理（+ 素材库沉淀的通用设定资料）

### 3.2 素材库 / 灵感库

| 库 | 内容 | 使用方式 |
|---|---|---|
| 素材库 | 场景卡、好词好句、金句、名称库（人名/地名/招式名）、对标拆解素材、驳回废稿 | 执笔/布景随时检索调用 |
| 具身细节库 | 按感官通道（视/触/嗅/听/味）× 场景类型（便利店/工地/医院/网吧…）组织的具身化细节（关东煮雾气、旧键盘键位磨损…） | 淬文强制每章植入 ≥2 个场景匹配细节 |
| 灵感库 | 创意火花、脑洞、废弃方案、读者反馈摘录 | 开新书/卡文时调用 |

- 前端新增「资料库」页面入口：三库分别管理（增删改查 + 标签 + 检索）
- 底层存储：世界库 → Memory world_model；素材库/灵感库 → 文件库 + Memory 索引（混合检索）

### 3.3 作品数据层（与三库严格分离）

| 数据 | 说明 |
|---|---|
| 规则基座 | 金手指与规则机制（能力/底层逻辑/代价与上限）——**锁定基线**，防战力崩溃 |
| 人物中心 | 主角/反派/女主或搭档/NPC 群像的人物卡（性格/行为逻辑/成长弧/关系网）——**锁定基线** |
| 世界观中心 | 力量境界/核心社会矛盾/主要地理舞台——**锁定基线** |
| 作品设定集 | 构世/塑像为【本书】产出的专属设定（可引用世界库规则为蓝本） |
| 人物表 / 地点表 / 势力表 | 本书已出现的动态人物、地点、势力（随创作增长） |
| 伏笔总账 | 伏笔状态机（埋下→待回收→已回收） |
| 线索矩阵 | 19 线叙事矩阵（见 §2.6） |
| 节奏矩阵 | 连载节奏与控字配置（见 §3.4）——运营层配置，可微调 |
| 时间线 / 章节正文 / 版本快照 | 本书创作数据 |

- **回写目标 = 作品数据层**：新人物/新地点/新伏笔成稿后写入本书作品档案
- 世界库永不接收创作产物（资料与作品、输入与输出严格分离）
- 知识中心（人物中心/世界观中心）＝ 一致性引擎事中路由的修正来源（见 §6）

## 4. Agent 记忆与上下文管理（每书隔离）

- **每部小说一个 Memory 命名空间（namespace）**：本书作品档案（作品设定/人物/伏笔/时间线）+ 文风 policy 各归各书，绝不乱串；三库参考资料按需共享

## 5. 版本管理（Plot Git · 类 Git 版本分支）

### 5.1 主版本线与基线锁定

```
主版本线（master）：基线快照 → 卷锁定 → 章锁定 → 成稿
   ├─ 试错分支：如"主角黑化版"→ 试验后 merge（局部采纳）或丢弃
   ├─ 设定修正版：改前置 → 强制新建版本线（旧线保留可审计）
   └─ Plot Diff：两版情节走向对比，供主编决策
```

- **基线快照**：立项环选定方案后生成，前置设定（基础信息/梗概/金手指/角色卡/世界观）成为不可变基线
- 基线之后任何修改动作被版本管理器**拒绝**，唯一合法路径 = 新建版本线（平行推演，互不污染，全部留痕）

### 5.2 能力清单

| 能力 | 实现 | 说明 |
|---|---|---|
| commit 快照 | 每章采纳后生成快照 | 复用/扩展 Dream 的 git 版本化机制 |
| branch 分支实验 | 支持"如果主角黑化会怎样"式的分支试错 | 实验分支不污染主线，可合并/丢弃 |
| lock 锁定 | 基线/卷/章三级锁定 | 锁定后该范围拒绝修改（防误改、防设定返工） |
| Plot Diff | 分支/版本间情节走向对比 | 供主编决定采纳哪条线 |
| 可审计 | 全部操作留痕 | 主编决策、专家调用、commit/merge/lock 记录 |

## 6. 一致性引擎与校验闭环（事中拦截 + 事后终验）

### 6.1 事中拦截（Interrupt Hub · 写作流内实时触发）

```
                    [ 正文生成中：检测到违规动作 ]
                                 │
                                 ▼
                     【一致性引擎 (Interrupt Hub)】
                                 │ (判定错误类型)
         ┌───────────────────────┼───────────────────────┐
         ▼                       ▼                       ▼
【路由 A：状态不符】      【路由 B：规则冲突】        【路由 C：人设偏离】
通知：人物中心(塑像)      通知：世界观中心(构世)     通知：剧情与场景中心(谋篇+布景)
   (提供替代道具/状态)    (提供规则合理解释)        (补充心理/动机过渡)
         │                       │                       │
         └───────────────────────┼───────────────────────┘
                                 ▼
                   【智能合成修正指令 (Patch Prompt)】
                                 │
                                 ▼
                   【正文创作中心 (自适应重流/局部修正)】
```

| 路由 | 判定 | 知识中心 | 修正方式 | 成本 |
|---|---|---|---|---|
| A 状态不符 | 人物当前状态矛盾 | 塑像（人物中心） | 提供替代道具/状态 | 轻量 |
| B 规则冲突 | 违反世界库预设/金手指代价 | 构世（世界观中心） | 提供规则合理解释 | 轻量 |
| C 人设偏离 | 行为无心理逻辑 | 谋篇 + 布景（剧情与场景中心） | 补充心理/动机过渡 | 中量 |
| D 风格违规 | 黑名单词/章末哲理/AI 句式 | 淬文（文风中心） | 局部洗稿不重写 | 极轻量 |
| E 基座违规 | 触犯锁定基线（金手指上限/已锁设定） | 主编（无权解释） | **回退重写该场景** | 重型 |

- D 类：去 AI 味从"全篇洗稿"降维成"局部替换"，黑名单命中直接词级/句级洗稿，不进重写流（省 token）
- E 类：兜底红线——锁定基线被触碰时知识中心无权"解释"，必须回退（"锁定"语义的强制执行点）

### 6.2 事后终验（审校专家 · 成稿后双基准全量查重）

```
[写作前] 执笔注入：世界库预设规则（硬约束）+ 本书作品档案（已写内容）
[写作中] 布景/淬文产出受世界库预设规则约束
[成稿后] 审校对照两个基准全量查重：
         基准① 世界库 —— 是否违反预设规则（如"无魔法世界出现魔法"）
         基准② 本书作品档案 —— 人物名/战力数值/地点/伏笔/时间线是否与已写内容矛盾
         ③ 伏笔未回收 / 回收矛盾（对照线索矩阵）
         ④ 逻辑漏洞
[回写]   新人物/新地点/新伏笔 → 写进【本书作品档案】（不是世界库）
         下次写作基于更新后的作品档案 + 世界库预设规则
```

- 事中拦截负责"别写错"（实时、轻量、路由到知识中心）；事后终验负责"查漏"（全量、兜底、双基准）
- 两道防线各司其职，共同解决"长篇连贯性崩坏"与"伏笔丢失"两大头号痛点

## 7. 补充机制清单

1. **反馈学习闭环**：用户评价 → policy 沉淀 → 影响后续执笔/淬文（复用现成反馈分类器）
2. **驳回品不删除**：进素材库/灵感库，可回收改写
3. **任务卡片协议**：派单带结构化 schema，专家按统一 schema 回传（调度器自动聚合的前提）
4. **章节状态机**：见 2.4
5. **模型分层路由**：灵思/谋篇/审校用便宜模型，执笔/淬文用强模型，控制成本
6. **进度仪表盘**：监工数据 + 主编控制台合一页（复用 history-dag 可视化）
7. **多书并行**：命名空间隔离天然支持
8. **素材库自动沉淀**：写作中产生的好词好句/场景自动回收
9. **去 AI 味引擎（De-AI Engine）**：由淬文主控，三道防护——
   ① 前置强约束：向模型注入黑名单（200+ 网文 AI 高频词：宛如/恐怖如斯/一抹…），禁用章末哲理总结
   ② 动作感官化（Show, Don't Tell）：强制将抽象心理形容词转换为具体物理动作与环境细节
   ③ 后置洗稿：打碎长难句，随机穿插短句与单字成段，模拟真实情绪断层与不完美口语特征
10. **具身细节库**：素材库子类，按感官通道 × 场景类型组织；淬文强制每章至少植入 2 个场景匹配的具身细节——解决"经验真空"：AI 缺的具身化细节靠语料喂养，不靠提示词
