# Project Context Pack Design

Date: 2026-08-10
Status: Approved for planning

## Problem

Memmy stores project-scoped memories and `turns/start` retrieves relevant memories, but external CLI agents can still forget facts the user has already established. The current project context pack is a panel read model: it selects memories with keyword patterns and renders them for inspection. It is not an authoritative project state and is not guaranteed to be injected into every Claude Code, Codex, or Pi turn.

Semantic retrieval remains useful for historical detail, but it cannot guarantee that a confirmed project goal, hard constraint, or active work item is present when the current prompt uses different wording. The system must separate facts that are always required from memories that are only relevant to a particular query.

## Goals

- Give each project one confirmed primary goal that every CLI agent receives on every turn.
- Support both short and long goals without truncating the authoritative source.
- Keep several work items under the primary goal while requiring the user to select the current focus manually.
- Keep confirmed decisions and hard constraints present independently of semantic similarity.
- Preserve ordinary memory retrieval as a supplemental source of history and detail.
- Make updates visible on the next turn without relying on hook-process caches.
- Preserve project namespace isolation, source-agent provenance, version history, and supersession relations.

## Non-goals

- Replacing the existing memory retrieval pipeline.
- Automatically changing the active work item based on conversational guesses.
- Treating unconfirmed model-generated summaries as authoritative project state.
- Introducing another project identifier or a second configuration system.
- Integrating an external agent runtime or control plane.

## Considered Approaches

### 1. Improve semantic retrieval only

Increase result limits, adjust ranking, or boost project-context tags.

This is the smallest change, but it cannot guarantee recall. A confirmed constraint can still be absent when the current prompt has low lexical or semantic similarity. It does not solve the reported failure mode.

### 2. Inject the complete project context pack every turn

Render all selected conventions, commands, architecture facts, tasks, and preferences on every turn.

This improves recall initially, but token usage and noise grow with the project. The current pack is also generated by keyword matching, so injection would make heuristic selections look authoritative.

### 3. Authoritative core plus supplemental retrieval

Maintain a compact, confirmed project state that is always injected. Preserve full goal details and ordinary memories for explicit or query-driven expansion.

This is the selected approach. It guarantees the presence of critical facts while keeping the stable per-turn payload bounded.

## Domain Model

### Project Goal

A project has at most one active primary goal.

Fields:

- `title`: one-line project direction; always injected.
- `summary`: stable concise representation; always injected.
- `detail`: complete source text for a long goal; available on demand.
- `acceptanceCriteria`: confirmed conditions for considering the goal achieved.
- `constraints`: confirmed project-wide hard constraints.
- `status`: `candidate`, `active`, `completed`, or `archived`.
- `version`: monotonically increasing within the project.
- `updatedAt`: last confirmed update time.
- `sourceMemoryIds`: evidence memories used to produce the proposal.
- `supersedesId`: previous confirmed goal version, when applicable.

A short goal can use the same text for `title`, `summary`, and `detail`. A long goal keeps the complete text in `detail`; `summary` is a bounded execution-oriented view, not a replacement for the source.

Only a confirmed goal can become `active`. A generated proposal remains `candidate` and must not enter fixed CLI context.

### Work Item

A project can contain several work items under its primary goal.

Fields:

- `title`
- `summary`
- `status`: `pending`, `active`, `blocked`, `completed`, or `archived`
- `nextStep`
- `acceptanceCriteria`
- `constraints`
- `updatedAt`
- `sourceMemoryIds`

Exactly zero or one work item is the project focus. Focus selection is an explicit user action. The system never switches focus from ordinary conversation.

### Confirmed Project Facts

Confirmed decisions and hard constraints remain separate normalized facts so they can be versioned and superseded independently. A new fact that conflicts with an active fact becomes a candidate for review; it does not silently replace the active fact.

## Proposal And Confirmation

Memmy may generate a goal proposal from:

- explicit user statements;
- current workspace-scoped memories;
- verified tool or test outcomes;
- current repository evidence when available through the authorized summarization flow.

A proposal includes the intended title, summary, detail, acceptance criteria, constraints, and evidence references. The user can approve, edit and approve, or reject it.

Approval activates the new version and records a supersession relation when replacing an older goal. Rejection leaves the current project context unchanged.

Work items may also be proposed, but selecting the current work item is always manual. Creating a work item and focusing it are separate actions.

## Context Pack Views

The project context pack has two views over the same authoritative records.

### Stable Turn Context

Injected on every `turns/start` call for a resolved project namespace:

- project identity;
- primary goal title and summary;
- primary goal status and version;
- selected work item summary, status, next step, and acceptance criteria;
- active confirmed decisions;
- active hard constraints;
- last confirmed update timestamp.

If no work item is selected, the turn continues normally. The context states that no work item is selected and gives a brief non-blocking reminder to select one. It must not infer a focus.

The stable context carries a distinct `project_context` marker and is rendered separately from historical memory. The host agent is told that it is current confirmed state, while retrieved memories are supporting historical evidence.

### Expanded Context

Fetched only when requested or relevant:

- complete long-goal detail;
- full work-item history;
- completed and archived work items;
- supporting memories and source relations;
- architecture and command details selected by normal retrieval.

The expanded view may be larger. It must not redefine the active goal or work item.

## Turn Start Data Flow

1. The CLI hook resolves the workspace path and opens the project-scoped session through `memmy.agent.v1`.
2. `turns/start` resolves the authoritative namespace.
3. The Memory service reads the current confirmed project state.
4. The service renders the stable turn context from active records.
5. Existing semantic retrieval runs for the current user prompt.
6. The response returns stable project context and supplemental memory context as separate fields or separately marked sections.
7. The hook injects both sections into the host CLI prompt, with the stable project context first.
8. The hook stores all injected memory IDs and project-state version in turn provenance.

The hook fetches project state on every turn. It does not keep an authoritative cached copy, so an approved update becomes visible on the next prompt.

## Precedence

For project state:

1. current confirmed project records;
2. current executable repository and verified tool evidence when a task explicitly checks them;
3. supplemental active memories;
4. historical or superseded memories.

If supplemental retrieval conflicts with confirmed project state, the host receives the conflict as historical evidence and follows the confirmed state. The conflict should be surfaced for review rather than silently merged.

A current repository check can show that stored project state is stale, but it does not automatically rewrite a user-confirmed goal or decision.

## API Boundary

The existing project namespace remains the owner of the records. The implementation should extend current Memory service and local API contracts instead of creating a parallel store.

Required operations:

- read the current project state and both context views;
- create a goal proposal;
- approve, edit-and-approve, or reject a proposal;
- create and list work items;
- select or clear the focus work item;
- update work-item status and next step;
- read version and supersession history.

Mutation requests must carry project namespace, source agent, adapter ID, request ID, and provenance. Read responses include the active version and generated timestamp.

## UI And CLI Behavior

The existing Project Context Pack dialog becomes an inspection and confirmation surface rather than a keyword-only report. It shows:

- current primary goal;
- pending proposal, when present;
- active work-item focus;
- available work items;
- confirmed decisions and constraints;
- version and evidence links.

CLI integrations require a small explicit command surface for selecting a work item and expanding context. Ordinary prompts remain unblocked when no work item is selected.

Exact command names are an implementation-planning decision and should reuse the existing Memmy command installation pattern.

## Failure Handling

- Memory unavailable: the hook must report that current project context was unavailable; it must not fabricate or reuse stale authoritative state.
- No confirmed goal: inject a compact `no confirmed project goal` state and continue.
- Candidate exists but is unconfirmed: do not inject candidate content as current state.
- Missing work-item focus: inject the primary goal and a non-blocking reminder.
- Context exceeds its stable budget: preserve title, hard constraints, active work item, and acceptance criteria; compact summaries deterministically. Full detail remains retrievable.
- Namespace mismatch: fail closed for project state; never inject another workspace's goal.
- Conflicting active records: return an explicit conflict status and exclude ambiguous records from authoritative prose until reviewed.

## Token Budget

The stable view must have a fixed character or token budget independent of the total memory count. Priority within that budget is:

1. hard constraints;
2. primary goal title and summary;
3. selected work item and next step;
4. acceptance criteria;
5. confirmed decisions;
6. status metadata.

Full goal detail is never destroyed to meet the stable-view budget; it remains in the expanded view.

## Verification

### Contract tests

- An approved goal appears in stable context for unrelated prompts.
- An unconfirmed candidate never appears in stable context.
- Updating a goal creates a new version and supersedes the previous version.
- A short goal preserves its complete text.
- A long goal keeps full detail while stable context uses the bounded summary.
- Selecting a work item changes only the focus section, not the primary goal.
- Clearing focus produces a non-blocking reminder.
- Conflicting or cross-namespace records are not injected as authoritative context.

### Hook tests

- Claude Code, Codex, and Pi receive the same project-state version for the same workspace.
- Stable project context appears before supplemental memory context.
- Every turn fetches current state; a newly approved update appears on the next turn.
- Turn completion provenance records the project-state version and injected source memory IDs.

### End-to-end scenario

1. Create a project with a long confirmed goal and a hard constraint.
2. Create two work items and manually select the first.
3. Start a fresh CLI session and ask an unrelated question.
4. Verify the injected context contains the goal summary, constraint, and first work item.
5. Switch to a different CLI and verify the same project-state version.
6. Manually select the second work item.
7. On the next prompt, verify the primary goal is unchanged and only the focus work item changes.
8. Propose but do not approve a goal revision; verify the revision is absent from stable context.
9. Approve the revision; verify it appears on the next prompt and the previous goal is retained in history.

## Migration

Existing memories remain unchanged. The current keyword-based context pack can continue as an expanded historical view during migration. No existing memory is promoted to authoritative state without confirmation.

The first project goal may be proposed from existing high-confidence project memories, but it requires user approval before activation. Existing project namespaces, provenance fields, memory IDs, and supersession records are reused.

## Completion Criteria

The feature is complete when a confirmed goal, hard constraint, and manually selected work item survive fresh sessions and CLI switches because they are present in every project-scoped `turns/start` response, while unconfirmed proposals and unrelated historical memories remain outside the stable authoritative section.
