## 本阶段结果

| 阶段 1 问题 | 阶段 2 行为 |
| --- | --- |
| A 的迟到失败可以覆盖 B 已成功的任务。 | 每次领取获得 owner 与唯一 token；完成、失败、延期和释放须匹配当前身份、leased 状态与有效截止时间。旧结果返回不计成功，也不计业务失败。 |
| 任务状态受到保护，但旧模型结果可能先写入记忆、向量和派生任务。 | 执行期间携带异步租约上下文，在实际 SQLite 写入前检查；过期或被接管后，迟到的业务写入被拒绝，事务中的修改回滚。 |
| 长任务或串行等待任务超过 60 秒可被重复领取。 | 主任务保留 60 秒租约，每 20 秒续租；过渡期对本轮尚在等待的已领取任务也续租。Embedding retry 的 5 分钟租约同样定期续租。 |
| 启动恢复无条件清除仍有效的租约。 | 保留有效租约，仅恢复已过期或没有截止时间的旧租约；永久失败 retry 不会因重启而复活。 |
| 普通临时失败连续三轮即可耗尽尝试。 | 失败记录 available_at，首次约 5 秒，随后指数增长，带 0.8–1.2 倍随机抖动，上限 5 分钟；未到时间不能重排，调度器按到期时间唤醒。 |
| 配置错误反复争抢任务，或终止后无法恢复。 | 主任务和 retry 均记录 configuration 阻塞，不消耗业务失败次数。有效模型配置变化后恢复原任务；同一错误配置不会每轮重新尝试。显式手工重试仍可恢复。 |
| 领取与失败次数混用，租约恢复也耗尽业务重试。 | 增加 failure_count、lease_count、lease_recovery_count；保留 attempts 的兼容用途。租约恢复不增加业务失败次数。 |

永久输入错误进入 dead letter；未知 job 类型立即终止，避免当作临时错误反复执行。既有配额错误 `40309` 的终止与可操作错误信息保留。

主任务仍使用旧的批量领取结构。本阶段通过续租保护暂时等待执行的任务；取消提前领取、统一入口并发、连续补位与 WRR/FIFO 按后续阶段实施。因此一万条积压中的调度饥饿问题仍由后续阶段解决，不能把本阶段验收等同于整个方案完成。

## 实现边界与衔接

- 新增 `job-lease-context.ts`；真实业务执行受保护，普通前台操作不需要任务租约。保护依赖工作方案既定的单 Memory 服务进程与同步 SQLite 写入边界，不持有跨模型等待的数据库事务。
- 任务完成后记账、清理日志等仍要继续执行。用量记账、outbox 交付、日志保留、历史快照压缩与新 worker 入口独立于业务租约上下文，避免旧租约终止这些基础设施操作。真实模型消耗即使发生于失效任务，也仍会记账。
- 模型配置指纹是摘要、演化、Embedding 和角色路由的 SHA-256；读取与真实模型执行相同的有效配置来源，包括 configLoader 变化，未把 API key 原文写入新字段。
- 配置错误仍以现有可操作失败状态呈现；配置变更后处理状态随原任务恢复。启动不会无条件解开配置阻塞。
- 同输入重复入队 retry 保留已有有效租约和退避；输入变更则明确变回 pending 并使旧 claim 失效。只修正租约状态一致性，未引入已取消的指纹去重/生产背压方案。

## 数据升级

Schema 从 v9 升到 v10，增加租约身份、到期时间、阻塞原因与独立计数；新增回收和可运行时间索引。沿用 MemoryDb 的升级前备份机制。

迁移测试实际恢复旧表形状后重新打开数据库，验证任务保留、旧计数回填、预迁移备份与再次打开的幂等性。历史 attempts 原本混合了领取和失败，旧业务失败次数按状态作兼容估算；新事件开始独立记录。

## 阶段 3 前的审查补修

阶段 1–2 审查确认了三个遗漏，已在独立补修提交中修正：

1. 启动占位摘要对账保留明确的失败处理状态，避免覆盖配置阻塞提示或为永久输入错误重新建任务。真实数据库关闭后重开验证：配置错误仍显示失败且可手动重试，永久 HTTP 400 不会被启动对账复活。
2. 每次实际模型执行记录当时的配置指纹。旧配置的在途请求晚到失败时，如果配置已经变化，仅重新排入该任务；当前配置本身的失败继续等待修复，避免无限重试。覆盖摘要和 Embedding retry，并验证不会误恢复另一个在新配置下确实失败的任务。
3. Embedding retry 每次领取生成独立唯一 token，检查、续租及全部结算均校验 token。即使同一 worker 在同一毫秒重领同一任务，旧凭据也无法写入新租约。数据库升级到 v11，保留尚有效的 v10 租约，过期后领取新 token。
