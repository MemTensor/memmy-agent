## 1. Agent 多轮读取

没有发现仓库 `.env`、默认 `~/.memmy/config.yaml` 或当前进程中的 API 凭据变量。已向用户询问模型和可用配置路径，尚未获得真实模型复测配置；没有搜索或使用其他应用的凭据。

新增 `tests/core/agent-runtime/long-document-review.test.ts`，通过真实 AgentRunner 运行工具调用。合成 DOCX 中分散放置四组已知数据：PE、持股比例、发行数量和募集金额。脚本模型只根据已收到的工具内容返回游标或提取答案，测试断言答案等于独立定义的标准值。

- 正向测试：跨越多轮读取、多个旧截断边界后，四组数据均可读回。
- 反向测试：脚本模型在第一段后直接回答，AgentRunner 仍结束任务。这证明当前运行时没有强制完整阅读；续读取决于模型行为。
- 此处没有调用真实模型，不能将脚本模型通过计入真实模型验收。

获取配置后的真实模型验收应运行至少“完整阅读”和“指定页核实”两类任务，保存模型名、提示词、工具轨迹、最终答案以及是否到达所需范围。完整阅读任务应核实结束标记；指定范围任务不应要求无关全文读取。若比较修复前后，应使用相同模型、设置和合成文档。

## 2. exec 输出截断及恢复

使用真实 Node 子进程输出合成报告，未 mock 命令执行。

1. 普通 `exec` 返回首尾片段，中部已知数据不在结果中，证明截断会丢失所需事实。
2. 重新执行相同的纯读取命令，将标准输出重定向到文件。
3. AgentRunner 使用 `read_file` 的行偏移分段读取，恢复全部四组数据；文件内容与源文本相同。
4. 独立测试确认：会话完成且输出截断后，`write_stdin` 返回会话不存在，不能恢复遗漏部分。

这条恢复流程仍由脚本决策驱动，未验证真实模型会自主采用。只应重跑确定没有副作用的文档提取命令，不能把这一策略无条件应用于任意命令。

### 新发现的单行文本缺口

生成一个超过 200,000 字符且没有换行的提取结果 `.txt`。当前文本读取逻辑只会减少“行数”；只剩一行时仍返回超出 128,000 上限的结果，同时标记 `End of file`，没有续读偏移。

运行时可能将此结果落盘为大工具结果引用，但再次用相同的按行工具读取超长单行，仍会遇到同一预算问题。因此“先保存文件再读”对普通多行文本有效，对超长单行文本还不可靠。应补充文本字符级分页或可靠的输出文件分块能力，再单独验证。当前复查测试明确记录这一已知缺陷；该测试通过表示缺陷可复现，不表示缺陷已经修复。

## 3. 性能测量

环境：macOS、Node.js v24.19.0。每个规模在独立进程中运行一次。使用真实 DOCX/PDF 解析器，默认每段 32,000 UTF-16 单元；分段内容的 SHA-256 与完整提取结果一致。PDF 文本均置于页面可见范围内。

| 样例 | 提取长度 | 读取次数 | 首段耗时 | 全文续读耗时 | 单次完整提取耗时 | 进程峰值 RSS |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| DOCX，约 25 万字符 | 253,375 | 8 | 29.8 ms | 148.2 ms | 15.5 ms | 507 MiB |
| DOCX，约 100 万字符 | 1,012,695 | 32 | 86.5 ms | 1,910.0 ms | 56.2 ms | 1,103 MiB |
| PDF，20 页 | 304,233 | 10 | 227.3 ms | 691.3 ms | 50.6 ms | 660 MiB |
| PDF，96 页 | 1,464,677 | 46 | 418.3 ms | 11,494.3 ms | 247.0 ms | 1,041 MiB |

注意：

- 峰值为整个测试进程的高水位，包含模块加载、样例创建和解析；开始读取前 RSS 约 473–492 MiB。不能据此断言存在内存泄漏，或把全部内存归因于本次改动。
- 单次提取在续读测量之后执行，是热运行参考，不是修复前版本的性能基线。
- 样例为重复文本，DOCX 压缩文件较小，未覆盖大量图片、复杂表格或扫描 PDF。
- 没有模型推理、网络往返或上下文压缩耗时；不能把此表当作真实会话的总耗时。
- 未发生超时或内容缺失，但反复全量解析导致明显累积成本。若继续优化，优先考虑有容量上限、能检测文件变化的提取结果缓存，或 PDF 按所需页提取；保持单次输出预算。
