调研结论 · Verdict

memmy-agent 天生自带 多 Agent 编排（SubagentManager）、任务分解 DAG、四层记忆引擎（世界模型）、技能系统 四大资产 —— "主编 + 11 位专家"不是从零造轮子，而是在现有 Agent 运行时上叠加一层"编委会编排层"。推荐路径：先以 Skills + 角色卡快速验证（2 周 MVP），再升级为 Agent Runtime 原生编排层（4–6 周完整版）。

一
项目本质：memmy-agent 是什么
一句话：本地优先的"个人记忆中心 + 通用 Agent 运行时"，定位类似 OpenClaw / Hermes，但核心卖点是跨 Agent 共享的记忆底座（MemOS）

memmy-agent 是一个 TypeScript npm workspaces monorepo（Node ≥ 22，Electron 桌面壳），由四个相互独立、可单独运行的子系统组成。它不是"聊天机器人"，而是一套完整的 Agent 运行时基础设施：记忆服务（:18960）、Agent 执行引擎、桌面本地后端（Fastify + SQLite）、前端 React 工作台，外加 CLI/TUI 与 OpenAI 兼容 API 等多个入口。

🧠

Memory Service（记忆底座）

独立本地服务，SQLite 存储 + LLM 驱动的四层记忆（trace 痕迹 / policy 策略 / world_model 世界模型 / skill 技能），向量 + 关键词混合检索，Dream 定时整理并做 git 版本化，支持一键回滚。目录 Memory/

🤖

Agent Runtime（执行引擎）

消息循环、工具注册、MCP、会话管理、自动压缩、技能加载、长期目标（long_task）、以及关键的 SubagentManager 子代理编排 与会话任务 DAG。App/memmy-agent/src/

🖥️

Local Backend（桌面后端）

Fastify + SQLite 的应用状态层：账号、模型配置、渠道接入、Agent 来源扫描、Skill 分发、面板与搜索服务，是前端所有操作的 API 网关。App/backend/src/

📖

Frontend Desktop（前端工作台）

React + Vite 的桌面 UI：聊天、记忆面板、历史 DAG 视图、工具管理、模型设置等页面；路由/状态/主题体系完整，可直接挂载新业务页面。App/frontend/desktop/

多入口形态（同一个 Agent 与记忆，处处可触达）

桌面 App、CLI/TUI（memmy agent）、OpenAI 兼容 API（memmy serve :18990）、消息渠道（Telegram / Discord / 微信 / 飞书 / 钉钉）共享同一套 Agents、记忆与配置 —— 这意味着小说写作系统将来可以"在电脑上写、在微信里催更、在 CLI 里批量跑"。

二
四大资产：与"编委会制写作"的天然契合点
以下能力全部已有现成代码，二次开发直接复用 —— 这是本方案可行性的核心依据

资产 ①　多 Agent 编排 —— 主编派单给专家的"操作系统"

App/memmy-agent/src/core/agent-runtime/subagent.ts 中的 SubagentManager 已经实现了完整的子代理生命周期：spawn 派发 → 并发控制（maxConcurrentSubagents）→ 状态跟踪（pending/running/complete/failed/cancelled）→ 生命周期钩子（subagentStart/subagentStop）→ 结果自动回传主会话。这恰恰就是"主编把任务拆给 11 位专家、收集成果、汇总交付"所需的全部机制。App/memmy-agent/src/core/agent-runtime/subagent.ts

🎯

spawn(task, label, …)

带描述、标签、会话归属地派发一个子代理任务；返回任务 ID，完成后自动通过消息总线把结果公布回主会话。

🛡️

并发与取消

按会话统计运行中任务，支持 cancelBySession 一键终止某会话的全部专家任务，防止失控。

🔌

生命周期钩子

AgentHook 提供 subagentStart / subagentStop，可挂接前端进度条、写作日志、token 统计。

配套的 Session DAG（App/memmy-agent/src/session-dag/）把会话中的任务组织成图：节点类型 task / subtask / decision，边类型 decomposes（分解）/ continues / blocks（阻塞）/ supersedes（取代）。一部小说的创作流程 —— 立项 → 世界观 → 人设 → 卷纲 → 章纲 → 正文 → 审稿 —— 天然就是一张 DAG，前端已有 history-dag-panel.tsx 可视化组件可改造成"创作进度看板"。

资产 ②　四层记忆引擎 —— 长篇小说的"设定保险柜"

长篇写作最大的痛点是一致性：人物名字、力量体系数值、时间线、伏笔回收。memmy 的记忆引擎恰好为此设计 —— world_model（世界模型）记忆层专门沉淀"环境的稳定事实"，可以直接存储世界观设定、人物档案、战力规则；policy（策略）层沉淀"怎么写更好"，用于学习用户的文风偏好；Dream 机制周期性把散落对话蒸馏进记忆并 git 版本化，可回滚 —— 等于给小说项目一个自动维护的"设定百科 + 版本控制"。Memory/src/algorithm/plugin-algorithms.ts

📜

trace → policy → world_model → skill

从交互痕迹逐级提炼可复用策略与稳定事实，写作经验会越用越多（LLM 归纳 + 置信度评分）。

💬

反馈学习

系统自带中英文反馈分类器（偏好 / 纠错 / 约束 / 正负评价），用户说"主角太圣母了"会被解析成可沉淀的策略。

🗂️

混合检索

向量 + 关键词 + LLM 相关性过滤三级召回，写作时自动注入相关设定，避免"写嗨了忘记设定"。

资产 ③　Skills 技能系统 —— 写作技能包的安装位

每个技能 = 一个含 SKILL.md 的目录（YAML frontmatter 声明名称/描述/依赖），Agent 在上下文中按需加载。工作区技能（~/.memmy/workspace/skills/）与内置技能（App/memmy-agent/src/skills/）双层加载 —— "网文写作技能集"（大纲模板、黄金三章 checklist、审稿清单）可以直接做成一组内置技能，用户还能自定义。加载器支持 requirements 检查（缺哪个 CLI/环境变量一目了然）。App/memmy-agent/src/core/agent-runtime/skills.ts

资产 ④　命令系统 + 人格模板 —— 角色卡与写作命令

命令路由支持 router.priority / exact / prefix 注册（App/memmy-agent/src/command/router.ts），现有命令如 /new、/goal、/dream、/history-dag 均按此注册 —— 新增 /新书、/大纲、/人设、/写正文、/审稿、/开编委会 等写作命令零架构改动。
人格系统：Agent 的"灵魂"来自模板文件（App/memmy-agent/src/templates/SOUL.md 定义我是谁/执行原则，templates/agent/subagent-system.md 定义子代理提示词）—— 每个专家 = 一份专属角色卡模板，这正是"主编 + 11 位专家"的实现入口。

二次开发路径：三条路，推荐 B
按改动深度与投入排序；三条路径可递进演进，不必一次到位
路径 A
MVP · 2 周
Skills + 角色卡方案 零架构改动，先跑通"编委会"体验

不碰运行时代码：把"主编 + 11 位专家"做成一组内置 SKILL.md（每个专家一份角色卡，主编一份编排指令），加一个 novel-orchestration 技能指导主编何时调用子代理。前端零改动（沿用聊天界面），写作产物落盘为 markdown 文件。

  • 优点：两天内可演示；全部复用现有 SubagentManager 与技能加载
  • 缺点：没有项目管理/章节存储/审稿看板；专家协作深度受单会话上下文限制
  • 落点：新增 App/memmy-agent/src/skills/novel-*/SKILL.md + 角色卡模板
路径 B ★
推荐 · 4–6 周
Agent Runtime 原生"编委会编排层" 核心方案

在 App/memmy-agent/src/ 下新增 novel/ 命名空间：NovelProject（项目与章节存储）、ExpertRegistry（12 位角色卡注册表）、ChiefDesk（主编调度器，基于 SubagentManager 派单 + 收集）、写作用户态写入 Memory 的 novel 命名空间。前端新增"小说工作台"页面（项目列表 / 章节树 / 编辑器 / 审稿面板 / 专家进度看板，复用 history-dag 可视化）。

  • 优点：专家是"一等公民"，支持并行写作、章节级审稿、设定自动记忆；能力完整可产品化
  • 改动：Agent 运行时新增 ~3–4 千行 + 后端写作 API + 前端 3–4 个页面
  • 落点：App/memmy-agent/src/novel/ · App/backend/src/services/novel-* · App/frontend/desktop/src/pages/novel-*
路径 C
重投入 · 8–12 周
独立小说引擎服务 产品级全栈

在 Memory 服务旁新增独立的 novel-service（自有数据库、章节版本控制、协作队列、导出管线：EPUB / DOCX / 全平台分发），前端做完整编辑器（分屏、批注、修订）。适合要做成独立产品的场景。

  • 优点：彻底解耦，性能与扩展性最好，可支持多人协作
  • 缺点：工作量大，前期与 memmy 现有能力重复度高

三个必须知道的工程前提

⚙️

并发上限默认 1

AgentDefaults.maxConcurrentSubagents = 1（config/schema.ts 第 304 行）。并行调用多位专家前必须调高，并考虑限流与预算控制。

💰

Token 成本线性放大

12 角色 × 每任务多次 LLM 调用。建议角色卡精炼（系统提示词控制在 800–1500 字）、审稿用便宜模型、正文用强模型的分层路由。

🔗

一致性命脉在 Memory

长篇设定一致性依赖 embedding 质量与 world_model 写入纪律：每章成稿后必须把新设定/新人物回写记忆，审稿编辑对照查重。

风险与对策
依据代码现状识别，非泛泛之谈
高
长篇一致性失控
几十万字后人物/设定/时间线漂移。对策：world_model 强制写入纪律 + 审稿编辑对照查重 + Dream 定期整理设定库，形成"写作 → 回写 → 查重"闭环。
高
Token 成本失控
12 角色串行会指数级放大成本。对策：模型分层（规划用小模型、正文用大模型）、专家并行上限、角色卡精简、按需召唤（不是每章都全员上阵）。
中
并发编排的工程复杂度
SubagentManager 已支持并发，但"主编收集多专家产出再汇总"需要任务结果协议（结构化 JSON 回传）。对策：为专家定义统一产出 schema（title/summary/detail/refs），主编按 schema 解析。
中
前端改动面
现有前端以聊天/记忆为核心，新增工作台涉及路由、导航、状态切片。对策：沿用现有 app-actions / app-state 模式新增 novel 切片，页面独立挂载，不侵入现有聊天流。
低
"AI 味"文本
网文读者对 AI 文风敏感。对策：文笔润色师角色卡内置去 AI 味清单（禁模板句式、禁滥用排比/感叹、口语化校验），并接入现有反馈分类器持续纠偏。

结语：这栋楼是为"编辑部"盖的

memmy-agent 的核心抽象 —— 记忆是"设定库"、子代理是"专家"、会话 DAG 是"任务看板"、技能是"写作手册"、SOUL 模板是"角色卡" —— 与小说写作系统的需求几乎一一对应。把它改造成"编委会制"写作系统，不是逆向重构，而是顺着现有架构做一层业务封装。

建议立即启动 M1：先写 12 份角色卡与 3 个写作技能，用两天跑通"开书 → 立项书"的完整编委会演示，再决定 M2 的工程化深度。每一步都有现成代码托底，风险可控。
