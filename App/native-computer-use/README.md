# Memmy Computer Use native runtime

Memmy builds its macOS, Windows, and Linux computer-control executables from the source in this directory. No Memmy release launches or packages the upstream npm binary. The internal MCP preset and registered tools use `memmy_computer_use`. Existing configs are renamed from `open_computer_use` by the v1.1.9 runtime migration. The helper command remains `open-computer-use`, and the native protocol still uses `OPEN_COMPUTER_USE_*` environment variables.

The packaged macOS helper is embedded as `Memmy Computer Use.app` but uses the main app bundle identifier `cn.memtensor.memmy`. This is intentional: Accessibility, Input Monitoring, and Screen Recording grants are one Memmy permission client and can be reused by the helper. Development copies may use `cn.memtensor.memmy.computeruse` (or the `.dev` variant); that identity is accepted only for local development and legacy shutdown/diagnostics.

Computer Use requires an unlocked console session. The former automatic lock-screen unlock/relock feature, authorization broker, guardian, and installation resources have been removed. `LockScreenState` still rejects desktop observation and input while macOS is locked or the session cannot be verified. The [legacy cleanup notes](lock-screen/README.md) cover administrator removal of an authorization component installed by an earlier release; cleanup is never run at startup.

The initial native code was imported from [iFurySt/open-codex-computer-use](https://github.com/iFurySt/open-codex-computer-use), tag `v0.3.5`, commit `386a260d1ab8b690adbbb27f7471595cf0c2b752`, under the MIT license in [LICENSE.upstream](LICENSE.upstream). Memmy owns subsequent changes to its bundle identity, branding, packaging, and host integration. The source remains here so native behavior can be reviewed and changed without replacing a third-party binary.

- macOS: `scripts/internal/mac/build-memmy-computer-use.sh` compiles Swift and signs `Memmy Computer Use.app`. The release packaging call passes `cn.memtensor.memmy` so the helper shares Memmy's system permissions; the script default remains the legacy development identity.
- Windows: `scripts/internal/win/build-memmy-computer-use.sh` compiles the Go and embedded PowerShell runtime to `memmy-computer-use.exe`.
- Linux: `scripts/internal/linux/build-memmy-computer-use.sh` compiles the Go and embedded Python runtime for both release architectures to `memmy-computer-use`.
- macOS grants for the packaged Memmy app and its helper use the single `cn.memtensor.memmy` identity. The host presents one Memmy-led guide covering Accessibility, Input Monitoring, and Screen Recording.
- Starting or opening the helper does not display an authorization window. `list_apps` needs neither macOS permission. For a real app, the accessibility tree and actions need Accessibility; a screenshot additionally needs Screen Recording. Memmy asks for target-app consent before an operation, then guides only the missing permission that operation needs. `get_app_state` can return the accessibility tree without a screenshot unless `require_screenshot=true`. `doctor` only reports status.
- Windows 11 has no equivalent global Accessibility/Screen Recording toggle for this Win32 runtime. Its UI Automation and screenshot path uses the signed-in desktop session. Elevated windows and the UAC secure desktop remain outside normal user-level automation. The window-message fallback checks `PostMessage` failures and reports UIPI access denial instead of claiming that a blocked click or keystroke succeeded; see Microsoft's [PostMessage documentation](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-postmessagew).

On macOS, a coordinate click may use AX only for a control at that point. A window or container is not permission to press unrelated descendant buttons: WPS's template cards can be absent from AX while the tab-close button is present. Such cards use the targeted mouse path. Screenshot pixels are converted to window points once, including on Retina displays. A successfully submitted AX click is followed by observation; a slow or unchanged snapshot never triggers a second mouse click. SkyLight clicks omit the out-of-window Chromium primer by default, and an error after mouse-down or during focus cleanup cannot fall through to another click transport. These safeguards have source-level regression coverage; installed WPS creation and concurrent-user acceptance still require testing the matching signed package.

On macOS and Windows, an action is withheld only when its input would reach a different target than the one observed. Live apps constantly change banners, helper windows, focus, selection, document text and unrelated accessibility nodes, so those changes never block an action; the action result shows them. Every action keeps its observation token and exact process/window binding, and recent observations of a window stay addressable, so actions generated from one state resolve their indices in that state. An element action follows the observed native accessibility object (the UI Automation runtime ID on Windows) to its current index and is withheld only when that object, or its role or control type, is gone. A coordinate action is withheld when the window was resized or when new content covers the target region; a caret, hover tint or antialiasing difference does not count, and choosing the same target again from the returned state sends it, so animated targets stay reachable. On macOS, keyboard input reaches a background window under the same synthetic key focus a background click uses, without activating the app. `type_text` types keystrokes into any focus, including document pages such as Word's or WPS's that expose no text role. With `paste: true` it enters the text through the app's paste command instead, which a slide canvas such as PowerPoint's in the background accepts while dropping keystrokes: the text is supplied only when the app reads it, then the user's clipboard is restored. Which to use is the caller's choice; results report what changed. A background pointer click into an app that ships a Chromium renderer helper (a browser, an Electron app, or an app with an embedded engine such as WPS) first sends an off-window press and release that satisfies Chromium's user-activation gate; Office maps that point onto its close button and ships no such helper, so its clicks omit it. An element click whose point is covered by another element, such as a floating bar over a list, is refused instead of being delivered to the element on top. A dialog that closes after the action is reported as a result, not as a withheld action. Apps are launched and their windows recovered without activation, and no click result suggests `foreground=true`; it stays an explicit last resort. On Windows, the runtime still checks at dispatch that the keyboard receiver is the same window and UI Automation object and that the owned-popup group under a coordinate is unchanged, because a separate PowerShell process sends the input a moment after the last observation; background text entry there remains limited to native Edit/RichEdit controls or a writable UI Automation value. `click`, `type_text` and `press_key` with `foreground=true` wait for a pause in the user's input, bring the target window to the front, send one uninterruptible real input to the window's own focus, and hand the foreground back; that reaches documents, Chromium pages and modifier shortcuts, which window messages cannot. Source and fixture tests do not replace installed macOS and Windows acceptance.

When an observation is stale, the MCP transport returns a structured state with `noActionDispatched`, a new `observationID`, and ordinary image content. The Agent can inspect that state before selecting another action. The transport must not stringify the native error object or hide the image and token inside an error message, and it never automatically replays the rejected action.
